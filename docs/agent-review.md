# Agentic review operating contract

The engine reviews introduced correctness and security defects using an immutable diff and source checkout. Findings are advice; a completed run does not establish recall or authorize a merge.

## Commands and trusted policy

Only an original, unedited `/review`, `/review deep`, `/review codex`, or `/review codex deep` comment by the designated maintainer qualifies. The login and numeric ID, human account type, organization association, event type, first run attempt, open PR, and same-repository origin must match. Python re-fetches the triggering command and checks its body and timestamps again before inference and publication. Fork and closed PR commands produce a failed admission job with a fixed reason, without supplying provider secrets.

The exact caller template, named secret mappings, permission ceiling, and immutable shared-engine pin remain mandatory. The credential-free source helper checks GitHub's loaded reusable-workflow identity before engine checkout. Command policy comes from the immutable loaded default-branch revision. For inline replies, executable source is selected before checkout; the loaded merge-ref caller is validated as bounded data and policy comes from a separately resolved immutable default-branch revision. See GitHub's [issue-comment contract](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment), [reusable workflows](https://docs.github.com/en/actions/concepts/workflows-and-actions/reusing-workflow-configurations), and [job identity context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#job-context).

Caller profiles permit only `[review] instructions` and `[ignore] glob`. The existing 65,536-byte bounded reader rejects symlinks in every path component, non-regular files, malformed TOML, and unsupported fields. Profiles cannot supply Python, tools, callbacks, model policy, spending limits, credentials, or a publication destination.

## Repository learnings

The optional learnings credential uses the caller's `AGENT_REVIEW_LEARNINGS_CLIENT_ID` configuration variable and the `AGENT_REVIEW_LEARNINGS_APP_KEY` workflow-call secret for the GitHub App installed on `pipelab-org/agent-review-learnings`. Set the organization variable to `Iv23li5uNkpZDatWI5To` and grant the caller repository access. Until that variable is available, the engine falls back to the existing `AGENT_REVIEW_LEARNINGS_APP_ID` secret. A set variable always wins, so a wrong client ID there hides a working legacy secret; the review summary then reports no learnings loaded. Credentials are available only when the private key and either identifier are present. `GITHUB_TOKEN` can't read that private repository. The pinned official [create-github-app-token v3.3.0 action](https://github.com/actions/create-github-app-token/releases/tag/v3.3.0), commit `64ab729a6294000f5aa4a4bc0b73d1f32bc45510`, mints an installation token for that owner and that repository only, with Contents:read and Metadata:read. The workflow revokes the installation token with `DELETE /installation/token` immediately after fetch and retains the action's job-end revocation as a backup. Revocation uses three attempts with a 15-second request timeout, two-second backoffs and a one-minute step ceiling (operator policy). Only HTTP 204 confirms revocation; an unconfirmed revoke fails the job before the PR head checkout or inference. The trusted notifier posts a fixed incomplete notice asking for a fresh review command, or for a new reply in the thread when an inline answer was refused; Actions reruns are refused. Revocation also runs whenever the mint step left a token, even if that step failed. After a successful early revoke, the action's job-end `Token revocation failed: ...` warning is expected because the token has already been revoked. Both revokes remain enabled.

The action's [entry point](https://github.com/actions/create-github-app-token/blob/64ab729a6294000f5aa4a4bc0b73d1f32bc45510/main.js#L22) selects a nonempty client ID before the legacy App ID; [both reach the same authentication parameter](https://github.com/actions/create-github-app-token/blob/64ab729a6294000f5aa4a4bc0b73d1f32bc45510/lib/main.js#L37-L41). The engine supplies either value through `client-id` and omits the deprecated `app-id` input, because the [runner warns whenever that input is supplied](https://github.com/actions/runner/blob/110142c2c501c6ae9373d553efa826bedbaab5f7/src/Runner.Worker/ActionRunner.cs#L189-L196), including an empty value. Reusable workflows [read configuration variables from the caller's repository](https://docs.github.com/en/actions/reference/workflows-and-actions/variables#configuration-variable-precedence), so callers need no new input or secret mapping. Existing caller templates and the legacy secret mapping stay valid.

Each inference job mints and fetches before preparing its prompt. Only fetch and the next revocation step receive the installation token through their step environments. Revocation runs before checking out the PR head and before inference; neither the model step nor any PR-code environment receives the token or the App key. Python 3.12 and the hash-pinned engine dependencies remain installed before steps that import third-party modules. The stdlib fetcher resolves the learnings default branch once, then fetches exactly `maintainers.toml` and `repos/<github.repository>.toml` at that full commit. It writes a temporary snapshot under `RUNNER_TEMP` with owner-only permissions, follows no repository rename aliases and refuses redirects. Preparation loads and selects entries, then removes the raw files and their directory before any model runs. A deletion failure stops preparation. Only selected prompt text and safe metadata survive in the plan. Review, reply and follow-up verification inference never reopen the raw snapshot.

The schema follows the learnings repository's README and validator: each entry has a unique ID, a supported status and kind, nonempty text, an HTTPS source, a valid teacher login, and TOML `added` and `review_by` dates in order. Only `active` entries approved by an account in the same snapshot's `maintainers.toml` load. Approval logins compare without case. Fetch records one UTC evaluation date in the local snapshot. Preparation uses that date to select entries. Inference consumes the prepared selection, including runs crossing midnight. A `review_by` equal to that date is still valid; an earlier date expires the entry. Proposed and retired entries never load. A malformed file or any validation failure loads no entries from that file.

An entry without `paths` applies repository-wide. Otherwise at least one glob must match a changed Git path. Matching uses Python's case-sensitive `fnmatchcase`, the repository's existing exclusion-glob convention: `*` and `**` span directories. Review bundles use the files in their admitted diff; inline answers use the merge-base diff at the captured head.

Both Claude and Codex receive each selected ID, kind, text and source inside a labeled untrusted-data section. Learnings never filter, match against, hide, drop or downgrade findings. They can't authorize thread resolution. Review and reply prompts carrying learnings state that output is public and must use code evidence only. They forbid quoting, paraphrasing, listing or citing learning text or IDs, and require refusing disclosure requests with a pointer to code evidence. A model that disagrees with a learning saying a pattern is fine must explain why the code supports its finding. Follow-up thread verification adds the same public-output instruction whenever the review loaded learnings.

Missing credentials, mint failures, a missing repository file, fetch failures, malformed TOML and validation failures all proceed with no learnings. The combined raw TOML byte bound derives from the depth's existing `max_model_tokens - max_output_tokens` input allowance. The same bound applies to network reads, and exact rendered learning bytes count in `build_bundle`'s existing full-prompt measurement, including the schema. If the context still doesn't fit after the normal full-file-to-region fallback, the engine removes the optional context and sizes the ordinary review again. Inline answers omit learning context if it exceeds their existing prompt allowance.

The public summary's Review details says `Learnings: N loaded from agent-review-learnings@<sha7>` or `Learnings: none loaded (<fixed reason>)`. Reasons come from a fixed allowlist; private files and exception text aren't echoed. Inference removes selected text from the on-disk plan before launching a model. Each Codex pass runs with a disposable copy of its trusted home and a disposable output directory; cleanup removes prompts, sessions and other runtime files before another pass starts. The published artifact omits that raw context and retains only the count, fixed reason, revision, digest and exact byte allowance. The publisher uses those bytes to reproduce the same bundle sizing without a private credential or another network lookup. These metadata fields are strictly validated and bound to the job's learning revision.

Review context retains the full learnings commit for provenance and public reporting. Coverage reuse compares a digest of the two fetched files' SHA-256 content digests and eligible entries; a missing file has a fixed `absent` marker. Commits touching other callers' files leave that identity unchanged. Changes to either fetched file or entry expiry invalidate earlier coverage. Preparation records that safe identity in a trusted step output. Inference compares the plan's identity against that output without reopening raw files, and publication receives the same identity. Thread ownership continues to ignore learnings fields.

## Per-depth operator limits

The trusted central `.github/pr-agent.toml` contains `review_depth.default`, `review_depth.deep`, `review_depth.codex`, and `review_depth.codex-deep`. Each table must contain these settings:

| Key suffix | Accepted value | Scope |
| --- | --- | --- |
| `max_turns` | Positive integer; booleans, strings, and fractional values are invalid | Each independent pass |
| `max_budget_usd` | Positive finite numeric USD amount; booleans and strings are invalid | Each independent pass |

Errors name the complete key, for example `review_depth.default.max_budget_usd`. There are no defaults or environment overrides. The shipped config sets both for every depth: 40 turns, USD 5 per default pass, USD 9 per deep pass, USD 2 per codex pass, and USD 2 per codex-deep pass. The owner approved the Claude turn limits on 2026-10-28 from measured evaluation runs and raised the Claude budgets on 2026-10-31 for the larger input allowance and the provisional Codex values on 2026-10-30 from a partial evaluation run. The derivation is in `.github/pr-agent.toml`. Removing either key makes the engine refuse inference for that depth.

Default review runs two fresh Sonnet processes at high effort: one investigates changed decisions and their boundary inputs, the other state and representation lifecycles (writers, readers, copies, reload, rollback, recheck interleavings). Every pass first searches for counterexamples and then decides what to report. Deep review runs one Opus process. Codex review runs one GPT-6.1 Terra pass at high effort; codex-deep runs one GPT-6.1 Sol pass at medium effort. A review's maximum configured USD allowance is **passes × max_budget_usd**. Claude's client estimate and Codex's monitored usage estimate can overshoot while an API request is in flight; this allowance is not a guaranteed invoice ceiling. Provider account/project limits remain the billing backstop.

The operator settings are `config.max_model_tokens` (272,000, overridden to 516,000 by `/review` and `/review deep`), `config.max_output_tokens` (16,000), and `config.ai_timeout` (900 seconds per pass). The review job has a 65-minute limit (two passes, thread verification and a full GitHub wait budget of one `ai_timeout`, plus setup) and the reply job 35 minutes (one call and the wait budget); the publish jobs make no provider calls and keep 25 minutes. These are operator settings, not advertised model capacities. The output schema permits six candidate findings per pass, ranked by confidence. The union may contain up to passes × six findings.

There is no automatic provider rollover or paid retry. Provider, parsing, tool, timeout, and limit failures require a new operator request after diagnosis. A failed Codex pass reports Codex's own recorded error category, such as a rate limit, a dropped response stream or a rejected key, with its HTTP status when Codex recorded one; provider error text is never published. An error event without a category reports "Codex reported an API or runtime error; pass incomplete", and an unsuccessful Codex exit without one still points at the provider account, read-only sandbox and schema. A failed Claude pass likewise reports Claude Code's own recorded classification: the assistant error category (such as a rate limit, a billing error or a rejected key), otherwise its terminal reason or result subtype, with the HTTP status when one was recorded. Provider error text and the result's error list are never published; a failure without a known classification keeps the fixed generic message. The second Anthropic key remains a legal caller mapping for compatibility but is not used for a hidden second attempt.

## Bundle and source access

The bundle uses `merge-base(head, base)..head`, or the verified prior head for an incremental review. It contains each changed file's full UTF-8 head content and patch. When full files exceed the configured input allowance, they are replaced by every changed region with Git's default three context lines. Remaining oversize input fails as incomplete; no patch or changed region is silently dropped. A depth may set its own `max_model_tokens`. The Claude depths use 516,000, a 500,000-byte input allowance plus the output reserve, because Claude's [long-context pricing](https://platform.claude.com/docs/en/about-claude/pricing#long-context-pricing) bills the full 1M window at standard rates; the engine refuses a Claude allowance above that window. The Codex depths keep 272,000 because OpenAI's [pricing](https://developers.openai.com/api/docs/pricing) bills the whole request at long-context rates above 272K input tokens. A change too large for the requested depth's allowance fails as incomplete; `/review` and `/review deep` accept larger changes than the Codex commands. The prompt names every file sent only as regions and asks for ranged reads around each changed region. Because every changed region is already in the bundle, a region-only file that no pass opened does not discard the review; the summary names it so reviewers can see how deep the pass went. UTF-8 byte length supplies a conservative token-planning bound without inventing a characters-per-token ratio; the full prompt and schema are checked before the CLI starts. Excluded files are recorded explicitly. Unexcluded binary, symlink, and submodule changes fail before inference.

The head is checked out below the workspace root with checkout credentials disabled. The workspace root is a base checkout. Only pinned engine code executes to construct the bundle or publish findings. Source reads and searches are untrusted input to the reviewer. The caller profile's instructions append to the central review rubric; source text cannot change runtime settings.

Claude starts in the head directory in restricted mode with only Read, Grep, and Glob, an empty strict MCP configuration, no slash commands, no session persistence, and no user/project/local settings. GitHub and membership credentials are removed from its environment. Output tokens come from the central setting, and automatic compaction is disabled. Each successful pass must have native successful Read tool results for every non-deleted changed file, not merely a model-authored list of files.

Codex runs with the head checkout as its working directory, so unqualified reads resolve in the PR head and receipt paths outside it are rejected. Its home is copied from trusted workflow files, never from the PR. The action selects `:read-only`, drops sudo and host capabilities, and passes the trusted output schema. The engine never intentionally executes PR scripts. A read-only sandbox constrains filesystem writes and direct network access; it is not a promise that instruction files cannot influence model text. Codex's normal AGENTS.md discovery is independent of write permissions. The central home disables project-document loading as defense in depth, and PR instruction files remain untrusted review data.

## Results, failures, and publication

Each findings file contains the merged findings plus one receipt per expected pass. A receipt records provider, configured model, strategy, native turn/inference-cycle count, successful file reads, token usage, estimated USD usage, and completion status. Claude's reported model must match policy. Codex requires one fresh native rollout with matching model and complete JSON. The publisher independently reconstructs the immutable bundle, validates schema and receipts, and rechecks the live PR and triggering event. Missing output, extra or truncated JSON, duplicate keys, invalid findings, missing passes, missing usage, stopped runs, API errors, and exceeded budgets fail closed.

Only the publisher has GitHub write permissions. It receives no provider secrets. It downloads this run's immutable artifact, then uses the existing verified publication semantics: partial or ambiguous writes abort, successful inline roots are re-read and bound by ID, review ID, body digest, path, and commit, and no ambiguous write is retried. Changed lines can anchor resolvable threads; related-source findings remain in the summary at their actual head locations. Exact prior findings stay in the summary with their full text without opening another identical thread; an earlier thread is not proof the text is still visible, because GitHub outdates a thread whose line is rewritten. Anchored findings whose line ranges overlap in the same file share one inline thread; each remains a separate finding in the summary and completion record. No model challenge can veto a candidate.

The summary opens with a one-line count and a table of findings (confidence, title, head location, and where it is discussed). Full text appears in the summary only for findings that have no thread on a changed line; inline findings are not repeated. Reviewed commits, policy, scope, exclusions, and unopened regions sit in a collapsed details block. After a successful publication the publisher hides earlier success statuses backed by verified completion records for the same policy with GitHub's [minimizeComment](https://docs.github.com/en/graphql/reference/issues#mutation-minimizecomment) mutation. Earlier summaries stay visible, because a later review that omits a finding or coverage gap does not establish that it was resolved; pending or incomplete notices and unverified bot comments also stay visible. This run's status stays visible so the failure notifier can update it if the completion upload fails. Hiding never changes a comment body, so digest-bound records stay verifiable; comments created after this run's status, and comments by any other author, are left alone. A refused hide leaves the remaining comments visible and does not fail the review.

A successful summary retains the `agent-review-result:v1` marker and a v2 completion payload, with a separate `agent-review-status:v1` success line. The digest covers the complete summary including its appended payload. The uploaded `agent-review-completion/completion.json` names source, profile, central config, base/head, depth, models, roots, scope, run, findings, and receipts. Deleted, edited, stale, failed, or unverified summaries never suppress a review.

Verified identical snapshots reuse their completion chain without inference. An eligible head advance reviews an immutable delta; missing proof, policy change, divergence, or changed merge-base context forces a full review. Every chain is checked back to its full review using immutable commit comparisons and run/artifact provenance. Unchanged snapshots perform no thread verification; this is a known limit. Concurrent requests can invalidate an old prepared scope; it fails before publication rather than certifying stale coverage.

Open threads are discovered with GitHub's [reviewThreads connection](https://docs.github.com/en/graphql/reference/pulls#object-pullrequest) and [thread state](https://docs.github.com/en/graphql/reference/pulls#object-pullrequestreviewthread). REST review comments have no resolved state. Eligible roots must match verified completion records by comment ID, review ID, original commit, path, and body digest, with the bot identity verified on both root and review. GitHub moves a live comment's `commit_id` when the head advances, so ownership uses `original_commit_id`, the REST counterpart of [originalCommit](https://docs.github.com/en/graphql/reference/pulls#object-pullrequestreviewcomment). Grouped roots must reconstruct exactly from their recorded findings; ambiguous groups stay open. Only threads GitHub reports as `isOutdated`, meaning the code at that location changed, are verified; a fix made elsewhere leaves the thread for a person to resolve.

When review inference runs and eligible threads exist, one additional batched verification strategy uses the hosting depth's provider, model, sandbox, transcript-derived receipts, and existing turn, dollar, token, and timeout limits. Default and deep use Claude's restricted file tools; Codex depths use the existing read-only action runner. This adds at most one per-pass allowance to a review. No provider credential crosses to the other provider. Oversized prompts, provider stops, malformed output, missing receipts, or unavailable GitHub state skip verification with the fixed notice `Thread follow-up verification unavailable; threads were left open.` They never invalidate an otherwise successful review.

The verification output contract is `{threads: [{thread, status, evidence}]}`, with status `fixed`, `present`, or `unclear`. Evidence entries carry `{finding, path, line, change}`: a zero-based index into that root's reconstructed findings, a head source path and positive line, and a concrete explanation of what changed. `fixed` requires evidence for every carried finding, successful file-read receipts for the cited paths, and confirmed source lines at the captured head. Every finding needs at least one evidence entry at its own recorded path; related paths can supplement it. Without that entry, verification becomes `unclear` and a fixed reply leaves the thread open. These checks bind evidence to code, but resolution remains a model judgment, as with CodeRabbit's documented [Auto-Resolve](https://docs.coderabbit.ai/changelog). The pull request author controls both the code the model reads and which threads become outdated, so automatic resolution is a convenience, not a security sign-off; a maintainer should still check resolved security findings before merging. Resolved threads remain in the PR and can be reopened. Silence, missing results, or omission of a finding from a later review never establishes a fix.

Only `fixed` threads receive a reply and GitHub's [resolveReviewThread mutation](https://docs.github.com/en/graphql/reference/pulls#mutation-resolvereviewthread). The publisher rechecks head, ownership, root text, reconstructed findings, and open thread state, publishes a pending reply, then edits and re-reads the completed evidence reply before resolving. The `agent-review-verified:v1` reply marker binds root and head. A prior completed verified answer at any head (pending or incomplete verification replies do not count), or a resolution-attempt marker, prevents all later automatic resolution of that root, including a different review depth at the same head and code-reading replies. A thread a person reopens is never auto-resolved again. A failed resolve needs a person or a new `/resolve` command. An exact existing answer can be reused for publication only; it never authorizes a second resolve. `present` and `unclear` produce no reply or state change. Unowned, edited, digest-mismatched, unverified, or ambiguously reconstructed roots are never auto-resolved. A failure on one thread leaves it visible and does not stop the remaining threads; failures emit the fixed notice once per publication without failing the review. Earlier summaries stay visible.

The publisher neutralizes every HTML comment opener in model-controlled reply text and rendered evidence before publishing. Model text cannot create `agent-review-*` state. A verified marker is accepted only on the first line of a bot reply bound to the same root. A resolved marker is accepted only on the last line, with that root's publisher-written reply header on the first line. The remaining readable text must contain no HTML comments or other markers. The resolved marker records an attempted mutation and is written only after that call, including an ambiguous failure; success wording requires GitHub's confirmed response. Publication reads the PR-wide judgment history once from REST list fields without completing every PyGithub comment. Rechecks refresh only the target thread's comments, state, and ownership.

Inline replies retain re-fetch admission, current organization membership, verified root provenance, captured-snapshot checks, and triggering-comment deduplication. Earlier-head roots are eligible through their immutable original commit; the human reply's identity, body, commits, path, thread, and creation fields must still match its created event exactly. Inference reads the head checkout with restricted file tools, using the normal-depth Claude policy and transcript-derived receipts. It returns `{answer, resolve, reason, evidence}`; reason is `fixed`, `finding_wrong`, or `none`, and evidence follows the verification contract. Resolution requires evidence for every carried finding. Only a human-reported fix that the code confirms, on a thread GitHub reports as outdated, resolves the thread. A `finding_wrong` answer is posted with a note leaving the thread open for a maintainer: that the finding is wrong is the argument a change author makes over code the author controls, so model agreement never resolves it. A confirmed fix on a live thread is answered the same way. A disputed finding that remains valid receives an answer and stays open. The separate publisher repeats admission and ownership checks and verifies the published answer before resolving. An invalid or incomplete answer never resolves a thread; a resolution failure leaves the answer visible and thread open.

The host-only command failure notifier retains fixed messages, no provider secrets, no checkout, and no model output. Its scope covers source, admission, inference, and publication failures when Actions schedules it. Workflow cancellation, unavailable workflow syntax, runner failure, and GitHub outage can prevent notification; a failed or absent notification is never evidence of a clean review. An unconfirmed learnings-token revoke in an inline-reply job also receives the fixed incomplete notice. Other inline inference failures remain failed Actions checks and publish no answer.

An inline reply whose trimmed body is exactly `/resolve` requests explicit resolution of that owned thread. It is case-sensitive and modeled on the thread-local resolve described in CodeRabbit's [review commands](https://docs.coderabbit.ai/reference/review-commands); the local syntax is `/resolve`, and CodeRabbit's author-approval setting has no equivalent here. Only the pull request author or someone with write access, the people GitHub itself lets [resolve a conversation](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/commenting-on-a-pull-request#resolving-conversations), can have the bot resolve a thread, by `/resolve` or by a reply reporting a fix; anyone else gets an answer and the thread stays open. Authority is read from the pull request author and GitHub's [repository permission](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user) at publication and checked again just before the mutation; a failed lookup never authorizes. If the command ends without calling GitHub, its acknowledgment is edited to say resolution was not attempted. The command uses the existing reply job and permissions, skips inference and finding reconstruction, and retains organization membership, exact created-event binding, original-commit ownership, no-fork, and first-run admission. It may resolve a live or reopened thread. An already-resolved thread causes no write. Other text follows normal code-reading replies, not the command path. The publisher rechecks admission and thread state, posts a short acknowledgment, calls GitHub, then records the attempt and observed outcome. Non-members, edited comments, unowned roots, and forged command flags never authorize resolution. A repeated command event never retries an ambiguous write; a new admitted `/resolve` reply is an explicit new request.

GitHub reads retain bounded, header-directed throttle retries; writes are serial, paced by GitHub's documented one-second minimum, and never retried. The separate allowlisted outcome record excludes provider bodies, prompts, credentials, and arbitrary error text. See [REST API best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) and [rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

Tests cover merge-base divergence, full files and bounded regions, command routing, strict JSON, each receipt failure class, location/mechanism deduplication, tool forwarding, artifact/snapshot tampering, partial publication, follow-up deduplication, and completion parsing.
