# Agentic review operating contract

The engine reviews introduced correctness and security defects using an immutable diff and source checkout. Findings are advice; a completed run does not establish recall or authorize a merge.

## Commands and trusted policy

Only an original, unedited `/review`, `/review deep`, `/review codex`, or `/review codex deep` comment by the designated maintainer qualifies. The login and numeric ID, human account type, organization association, event type, first run attempt, open PR, and same-repository origin must match. Python re-fetches the triggering command and checks its body and timestamps again before inference and publication. Fork and closed PR commands produce a failed admission job with a fixed reason, without supplying provider secrets.

The exact caller template, named secret mappings, permission ceiling, and immutable shared-engine pin remain mandatory. The credential-free source helper checks GitHub's loaded reusable-workflow identity before engine checkout. Command policy comes from the immutable loaded default-branch revision. For inline replies, executable source is selected before checkout; the loaded merge-ref caller is validated as bounded data and policy comes from a separately resolved immutable default-branch revision. See GitHub's [issue-comment contract](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment), [reusable workflows](https://docs.github.com/en/actions/concepts/workflows-and-actions/reusing-workflow-configurations), and [job identity context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#job-context).

Caller profiles permit only `[review] instructions` and `[ignore] glob`. The existing 65,536-byte bounded reader rejects symlinks in every path component, non-regular files, malformed TOML, and unsupported fields. Profiles cannot supply Python, tools, callbacks, model policy, spending limits, credentials, or a publication destination.

## Per-depth operator limits

The trusted central `.github/pr-agent.toml` contains `review_depth.default`, `review_depth.deep`, `review_depth.codex`, and `review_depth.codex-deep`. Each table must contain these settings:

| Key suffix | Accepted value | Scope |
| --- | --- | --- |
| `max_turns` | Positive integer; booleans, strings, and fractional values are invalid | Each independent pass |
| `max_budget_usd` | Positive finite numeric USD amount; booleans and strings are invalid | Each independent pass |

Errors name the complete key, for example `review_depth.default.max_budget_usd`. There are no defaults or environment overrides. The shipped config sets both for every depth: 40 turns, USD 2 per default pass, USD 4 per deep pass, USD 2 per codex pass, and USD 2 per codex-deep pass. The owner approved the Claude values on 2026-10-28 from measured evaluation runs and the provisional Codex values on 2026-10-30 from a partial evaluation run. The derivation is in `.github/pr-agent.toml`. Removing either key makes the engine refuse inference for that depth.

Default review runs two fresh Sonnet processes at high effort: one investigates changed decisions and their boundary inputs, the other state and representation lifecycles (writers, readers, copies, reload, rollback, recheck interleavings). Every pass first searches for counterexamples and then decides what to report. Deep review runs one Opus process. Codex review runs one GPT-6.1 Terra pass at high effort; codex-deep runs one GPT-6.1 Sol pass at medium effort. A review's maximum configured USD allowance is **passes × max_budget_usd**. Claude's client estimate and Codex's monitored usage estimate can overshoot while an API request is in flight; this allowance is not a guaranteed invoice ceiling. Provider account/project limits remain the billing backstop.

The operator settings are `config.max_model_tokens` (272,000), `config.max_output_tokens` (16,000), and `config.ai_timeout` (300 seconds per pass). The workflow retains its 25-minute job limit. These are operator settings, not advertised model capacities. The output schema permits six candidate findings per pass, ranked by confidence. The union may contain up to passes × six findings.

There is no automatic provider rollover or paid retry. Provider, parsing, tool, timeout, and limit failures require a new operator request after diagnosis. A failed Codex pass reports Codex's own recorded error category, such as a rate limit, a dropped response stream or a rejected key, with its HTTP status when Codex recorded one; provider error text is never published. An error event without a category reports "Codex reported an API or runtime error; pass incomplete", and an unsuccessful Codex exit without one still points at the provider account, read-only sandbox and schema. The second Anthropic key remains a legal caller mapping for compatibility but is not used for a hidden second attempt.

## Bundle and source access

The bundle uses `merge-base(head, base)..head`, or the verified prior head for an incremental review. It contains each changed file's full UTF-8 head content and patch. When full files exceed the configured input allowance, they are replaced by every changed region with Git's default three context lines. Remaining oversize input fails as incomplete; no patch or changed region is silently dropped. 272,000 is the largest input billed at standard rates by both providers: OpenAI's [pricing](https://developers.openai.com/api/docs/pricing) switches to long-context rates above 272K input tokens, and Claude's [long-context pricing](https://platform.claude.com/docs/en/about-claude/pricing#long-context-pricing) bills the full window at standard rates. The prompt names every file sent only as regions and asks for ranged reads around each changed region. Because every changed region is already in the bundle, a region-only file that no pass opened does not discard the review; the summary names it so reviewers can see how deep the pass went. UTF-8 byte length supplies a conservative token-planning bound without inventing a characters-per-token ratio; the full prompt and schema are checked before the CLI starts. Excluded files are recorded explicitly. Unexcluded binary, symlink, and submodule changes fail before inference.

The head is checked out below the workspace root with checkout credentials disabled. The workspace root is a base checkout. Only pinned engine code executes to construct the bundle or publish findings. Source reads and searches are untrusted input to the reviewer. The caller profile's instructions append to the central review rubric; source text cannot change runtime settings.

Claude starts in the head directory in restricted mode with only Read, Grep, and Glob, an empty strict MCP configuration, no slash commands, no session persistence, and no user/project/local settings. GitHub and membership credentials are removed from its environment. Output tokens come from the central setting, and automatic compaction is disabled. Each successful pass must have native successful Read tool results for every non-deleted changed file, not merely a model-authored list of files.

Codex runs with the head checkout as its working directory, so unqualified reads resolve in the PR head and receipt paths outside it are rejected. Its home is copied from trusted workflow files, never from the PR. The action selects `:read-only`, drops sudo and host capabilities, and passes the trusted output schema. The engine never intentionally executes PR scripts. A read-only sandbox constrains filesystem writes and direct network access; it is not a promise that instruction files cannot influence model text. Codex's normal AGENTS.md discovery is independent of write permissions. The central home disables project-document loading as defense in depth, and PR instruction files remain untrusted review data.

## Vendor facts and pins

Checked against official documentation on 2026-10-28:

- Anthropic's [CLI reference](https://code.claude.com/docs/en/cli-reference.md) documents `--json-schema`, `--max-turns`, `--max-budget-usd`, `--tools`, `--disallowedTools`, `--strict-mcp-config`, and `--restricted`. Restricted mode requires at least 2.1.248. The workflow installs exact CLI version 2.1.312, resolved from the official npm package registry.
- `--allowedTools` only preapproves tool use; `--tools` restricts built-ins. MCP tools require a separate denial. The engine requests `Read,Grep,Glob` as its built-in file tools, denies `mcp__*`, and supplies an empty strict MCP config. The pinned CLI adds its own non-executing schema/deferred helpers, checked by the native dry harness. The [action usage guide](https://github.com/anthropics/claude-code-action/blob/main/docs/usage.md) documents forwarding CLI flags through `claude_args`; this engine invokes that CLI directly, so no action argument-merging layer can add tools.
- The [Anthropic action security guide](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md) recommends a base checkout at the workspace root and a separate PR-head subdirectory. It also warns that repository scripts and tool configuration remain untrusted even when some configuration paths are restored from base.
- Anthropic's [environment reference](https://code.claude.com/docs/en/env-vars.md) documents `CLAUDE_CODE_MAX_OUTPUT_TOKENS` and `DISABLE_AUTO_COMPACT`. The same reference documents zero request/timeout retries and a single structured-output attempt; the engine sets them explicitly. Its [cost guidance](https://code.claude.com/docs/en/agent-sdk/cost-tracking.md) explains that client estimates can differ from billing.
- The [Codex action README](https://github.com/openai/codex-action/blob/c05cfd74ad95c626cdf05c6685e62becc3bf7813/README.md) documents `permission-profile: ":read-only"`, `output-schema-file`, trusted `codex-home`, and the requirement to combine permission profiles with `drop-sudo` or a deliberately unprivileged user. The action is pinned to that full SHA, with CLI version 0.165.0 resolved from the official npm package registry. The setup step uses `safety-strategy: read-only` so sudo is still present when the engine launches Codex with `drop-sudo`. That launch removes sudo and starts Codex under `setpriv` with no_new_privs, cleared groups and empty capability sets; the pinned [runner](https://github.com/openai/codex-action/blob/c05cfd74ad95c626cdf05c6685e62becc3bf7813/src/runCodexExec.ts) refuses a launch-time drop after setup already removed sudo.
- OpenAI's [AGENTS.md guidance](https://developers.openai.com/codex/guides/agents-md) documents global and project instruction discovery. The [action security guide](https://github.com/openai/codex-action/blob/c05cfd74ad95c626cdf05c6685e62becc3bf7813/docs/security.md) treats PR-controlled instruction files as an injection source. Read-only permissions do not by themselves disable discovery.
- The pinned action's [runner](https://github.com/openai/codex-action/blob/c05cfd74ad95c626cdf05c6685e62becc3bf7813/src/runCodexExec.ts) selects the permission profile, schema, and privilege reduction. The workflow uses the action's setup-only form, then the same pinned runner under the engine's transcript monitor. The trusted action proxy table sets `request_max_retries = 0` and `stream_max_retries = 0` using the [documented provider settings](https://developers.openai.com/codex/config-reference); its context window comes from the central operator token budget. Native [protocol events](https://github.com/openai/codex/tree/rust-v0.165.0/codex-rs/protocol) supply successful command reads, configured model, inference cycles, and token totals. GPT-6 model metadata selects code mode, where commands run inside the `exec` tool; their reads come from the runtime's completed `CommandExecution` items with exit code 0 and Codex's own `read` classification of the command, resolved against the recorded working directory. Only plain literal `cat [--|-n] PATH` and `sed -n 'START,ENDp' PATH` commands count toward reads. Compound commands and pipelines don't count: Codex's display classification can include reads that shell control flow skipped, or whose failure another pipeline stage hid. Code-mode receipts also require the command's nonempty output to appear in the tool response returned to the model. Return it with `text(result)` or `text(result.output)`; discarded or truncated output that cannot be matched does not count.
- Codex's monitored estimate uses the configured model's [standard short-context rates](https://developers.openai.com/api/docs/pricing). Per million input/cached input/output tokens: gpt-6.1-sol $2/$0.10/$10, gpt-6-astra $10/$1/$50, gpt-6.1-terra $1/$0.05/$5, gpt-6-luna $0.10/$0.01/$0.50. Cached input is part of the reported input total and is charged at the cached rate. Reported cache writes add the model's 30-minute cache-write rate, even when already included in input, to avoid underestimating their higher rate. This estimate can overstate cost. Other models fail until a sourced price is added. Requests above 272K input tokens bill at long-context rates, so the engine refuses Codex inference when `config.max_model_tokens` exceeds 272000.

The argv harness checks subprocess arguments, working directory, and credential separation. A second harness runs the actual pinned native CLI against a local fixture API, without paid inference. It confirms the API inventory contains Read/Grep/Glob plus the CLI's non-executing schema/deferred format helpers, with no Bash or MCP tools; each API request uses the configured output-token limit. Forced Bash/MCP calls, outside-directory and symlink reads, PR startup hooks, and PR MCP configuration do not execute or expose the outside fixture. Native turn and budget stops produce failed results. API failures and invalid schema output stop after one fixture request; no provider or schema-repair retry is made. The StructuredOutput schema formatter is allowed as CLI infrastructure; it supplies no filesystem or network capability. Hosted-runner isolation, real provider acceptance, Codex action setup-only composition, and current account access remain smoke-test requirements.

## Results, failures, and publication

Each findings file contains the merged findings plus one receipt per expected pass. A receipt records provider, configured model, strategy, native turn/inference-cycle count, successful file reads, token usage, estimated USD usage, and completion status. Claude's reported model must match policy. Codex requires one fresh native rollout with matching model and complete JSON. The publisher independently reconstructs the immutable bundle, validates schema and receipts, and rechecks the live PR and triggering event. Missing output, extra or truncated JSON, duplicate keys, invalid findings, missing passes, missing usage, stopped runs, API errors, and exceeded budgets fail closed.

Only the publisher has GitHub write permissions. It receives no provider secrets. It downloads this run's immutable artifact, then uses the existing verified publication semantics: partial or ambiguous writes abort, successful inline roots are re-read and bound by ID, review ID, body digest, path, and commit, and no ambiguous write is retried. Changed lines can anchor resolvable threads; related-source findings remain in the summary at their actual head locations. Exact prior findings stay in the summary with their full text without opening another identical thread; an earlier thread is not proof the text is still visible, because GitHub outdates a thread whose line is rewritten. Anchored findings whose line ranges overlap in the same file share one inline thread; each remains a separate finding in the summary and completion record. No model challenge can veto a candidate.

The summary opens with a one-line count and a table of findings (confidence, title, head location, and where it is discussed). Full text appears in the summary only for findings that have no thread on a changed line; inline findings are not repeated. Reviewed commits, policy, scope, exclusions, and unopened regions sit in a collapsed details block. After a successful publication the publisher hides earlier success statuses backed by verified completion records for the same policy with GitHub's [minimizeComment](https://docs.github.com/en/graphql/reference/issues#mutation-minimizecomment) mutation. Earlier summaries stay visible, because a later review that omits a finding or coverage gap does not establish that it was resolved; pending or incomplete notices and unverified bot comments also stay visible. This run's status stays visible so the failure notifier can update it if the completion upload fails. Hiding never changes a comment body, so digest-bound records stay verifiable; comments created after this run's status, and comments by any other author, are left alone. A refused hide leaves the remaining comments visible and does not fail the review.

A successful summary retains the `agent-review-result:v1` marker and a v2 completion payload, with a separate `agent-review-status:v1` success line. The digest covers the complete summary including its appended payload. The uploaded `agent-review-completion/completion.json` names source, profile, central config, base/head, depth, models, roots, scope, run, findings, and receipts. Deleted, edited, stale, failed, or unverified summaries never suppress a review.

Verified identical snapshots reuse their completion chain without inference. An eligible head advance reviews an immutable delta; missing proof, policy change, divergence, or changed merge-base context forces a full review. Every chain is checked back to its full review using immutable commit comparisons and run/artifact provenance. Unchanged snapshots perform no thread verification; this is a known limit. Concurrent requests can invalidate an old prepared scope; it fails before publication rather than certifying stale coverage.

Open threads are discovered with GitHub's [reviewThreads connection](https://docs.github.com/en/graphql/reference/pulls#object-pullrequest) and [thread state](https://docs.github.com/en/graphql/reference/pulls#object-pullrequestreviewthread). REST review comments have no resolved state. Eligible roots must match verified completion records by comment ID, review ID, original commit, path, and body digest, with the bot identity verified on both root and review. GitHub moves a live comment's `commit_id` when the head advances, so ownership uses `original_commit_id`, the REST counterpart of [originalCommit](https://docs.github.com/en/graphql/reference/pulls#object-pullrequestreviewcomment). Grouped roots must reconstruct exactly from their recorded findings; ambiguous groups stay open. Only threads GitHub reports as `isOutdated`, meaning the code at that location changed, are verified; a fix made elsewhere leaves the thread for a person to resolve.

When review inference runs and eligible threads exist, one additional batched verification strategy uses the hosting depth's provider, model, sandbox, transcript-derived receipts, and existing turn, dollar, token, and timeout limits. Default and deep use Claude's restricted file tools; Codex depths use the existing read-only action runner. This adds at most one per-pass allowance to a review. No provider credential crosses to the other provider. Oversized prompts, provider stops, malformed output, missing receipts, or unavailable GitHub state skip verification with the fixed notice `Thread follow-up verification unavailable; threads were left open.` They never invalidate an otherwise successful review.

The verification output contract is `{threads: [{thread, status, evidence}]}`, with status `fixed`, `present`, or `unclear`. Evidence entries carry `{finding, path, line, change}`: a zero-based index into that root's reconstructed findings, a head source path and positive line, and a concrete explanation of what changed. `fixed` requires evidence for every carried finding, successful file-read receipts for the cited paths, and confirmed source lines at the captured head. These checks bind evidence to code; the model's interpretation still needs maintainer judgment. Silence, missing results, or omission of a finding from a later review never establishes a fix.

Only `fixed` threads receive a reply and GitHub's [resolveReviewThread mutation](https://docs.github.com/en/graphql/reference/pulls#mutation-resolvereviewthread). The publisher rechecks head, ownership, root text, reconstructed findings, and open thread state, publishes a pending reply, then edits and re-reads the completed evidence reply before resolving. The `agent-review-verified:v1` reply marker binds root and head. A rerun can reuse only the exact verified answer; an edited or incomplete marked reply blocks resolution. A thread that already carries a verified reply from an earlier head is never verified or resolved again, so a thread a person reopens stays open. A reply that resolves its thread ends with an `agent-review-resolved:v1` marker naming the root, and thread verification skips that thread at every later head for the same reason. `present` and `unclear` produce no reply or state change. Unowned, edited, digest-mismatched, unverified, or ambiguously reconstructed roots are never resolved. GraphQL, reply, or resolution failures leave remaining threads open and emit the fixed notice without failing the review. Earlier summaries stay visible.

Inline replies retain re-fetch admission, current organization membership, verified root provenance, captured-snapshot checks, and triggering-comment deduplication. Earlier-head roots are eligible through their immutable original commit; the human reply's identity, body, commits, path, thread, and creation fields must still match its created event exactly. Inference reads the head checkout with restricted file tools, using the normal-depth Claude policy and transcript-derived receipts. It returns `{answer, resolve, reason, evidence}`; reason is `fixed`, `finding_wrong`, or `none`, and evidence follows the verification contract. Resolution requires evidence for every carried finding. Only a human-reported fix that the code confirms, on a thread GitHub reports as outdated, resolves the thread. A `finding_wrong` answer is posted with a note leaving the thread open for a maintainer: that the finding is wrong is the argument a change author makes over code the author controls, so model agreement never resolves it. A confirmed fix on a live thread is answered the same way. A disputed finding that remains valid receives an answer and stays open. The separate publisher repeats admission and ownership checks and verifies the published answer before resolving. An invalid or incomplete answer never resolves a thread; a resolution failure leaves the answer visible and thread open.

The host-only command failure notifier retains fixed messages, no provider secrets, no checkout, and no model output. Its scope covers source, admission, inference, and publication failures when Actions schedules it. Workflow cancellation, unavailable workflow syntax, runner failure, and GitHub outage can prevent notification; a failed or absent notification is never evidence of a clean review. Inline inference failures remain failed Actions checks and publish no answer.

GitHub reads retain bounded, header-directed throttle retries; writes are serial, paced by GitHub's documented one-second minimum, and never retried. The separate allowlisted outcome record excludes provider bodies, prompts, credentials, and arbitrary error text. See [REST API best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) and [rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

## Validation and remaining live proof

CI installs hash-pinned Python dependencies and runs unittest discovery plus the provider/publication runtime suites. No PR-Agent installation or silent runtime skip remains. Tests cover merge-base divergence, full files and bounded regions, command routing, strict JSON, each receipt failure class, location/mechanism deduplication, tool forwarding, artifact/snapshot tampering, partial publication, follow-up deduplication, and completion parsing. Mutation checks neutralize schema validation and file-read receipt validation separately; each causes its negative test to fail. Fenced/truncated and empty-receipt replay fixtures remain; the retired PR-Agent replay CLI has no consumer and is removed.

The shipped limits are owner-approved (see above). Before repinning consumers, the operator must perform paid evaluation plus hosted smoke checks for actual provider acceptance, restricted tool behavior, native transcript and cost receipts, read-only permissions, membership visibility, immutable artifacts, and cross-repository publication. The native dry harness is `python scripts/test_provider_dry_run.py --claude "$(command -v claude)"` after installing the pinned CLI. It exercises the actual restricted CLI and local fixture API; it does not establish paid-model review quality or security isolation on a hosted runner.
