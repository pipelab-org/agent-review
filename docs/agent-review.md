# PR-Agent diff review

Comment `/review` or `/review deep` on an open pull request from the same repository. Only the designated maintainer's original comment qualifies. Edited comments, unsupported arguments, workflow reruns, other accounts, bots, plain issues, closed PRs, and fork PRs can't start a review. The workflow must already be on the default branch; a comment on the PR installing it doesn't exercise the proposed version. See GitHub's [issue-comment event contract](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment).

Findings appear on changed lines as resolvable review threads, with a preserved summary for findings that can't be anchored safely. A separate completion record names the captured base/head, reviewer source, caller profile revision and hash, actual models, reported token usage, and declared exclusions. Repeated commands for the identical completed snapshot link to that record without another inference. Running, failed, partial, stale, or unverified records never qualify for reuse. The bot-owned summary must still match the ID and content hash in its completion record; deleted, edited, or replaced summaries require another review. A changed base, profile revision/content, reviewer source, review depth, or central model configuration requires a full review. An eligible head advance can use the verified incremental chain described below.

This optional command can run alongside other review tools. It reviews a bounded diff plus the current text of changed files and of repository files the model requests in one source-read step. It can't search or execute the repository, commit repairs, approve a PR, or change labels. Only the exact `/review` and `/review deep` commands start reviews. Findings are advice and can be wrong; successful execution alone doesn't establish review quality or recall.

## Shared source and repository policy

[The caller](../.github/workflows/agent-review.yaml) delegates to [the reusable workflow](../.github/workflows/agent-review-reusable.yaml). This repository uses a local reference so its own caller loads the same immutable revision. Other repositories must use `pipelab-org/agent-review/.github/workflows/agent-review-reusable.yaml` at a full 40-character merged commit SHA, followed by the `# main` tracking comment. Never use an executing branch or tag reference. GitHub documents [local and remote reusable references](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_iduses).

The credential-free [source helper](../.github/workflows/agent-review-source.yaml) validates GitHub's loaded workflow identity. Its SHA selects the explicit `pipelab-org/agent-review` checkout at `trusted-agent-review`. Ordinary checkout inside a reusable workflow reads the caller, so it can't select the shared engine. For command events, the caller profile and caller workflow are checked out separately at the caller's captured default-branch `github.workflow_sha`. Inline events resolve and capture an immutable default-branch policy revision, and validate the loaded merge-ref caller as data against the exact template before loading that policy. Checkout credentials are disabled. Only Python from the shared source executes; caller files remain bounded data. See GitHub's [caller context and checkout behavior](https://docs.github.com/en/actions/concepts/workflows-and-actions/reusing-workflow-configurations#reusable-workflows) and [job workflow identity](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#job-context).

[Common configuration](../.github/pr-agent.toml) owns models, budgets, provider handling, restricted operation, output, telemetry, and the anti-injection rubric. [The repository profile](../.github/agent-review.toml) permits exactly these fields:

```toml
[review]
instructions = "Review material correctness defects against this repository's contracts."

[ignore]
glob = ["**/vendor/**"]
```

The profile can't change credentials, publishing target, admission, callbacks, approval, retries, models, or budgets. Unknown fields, malformed TOML, non-regular files, symlinks in any path component, and files larger than 65,536 bytes are rejected before inference. Instructions append to the common rubric. Exclusions are explicit and disclosed separately from files omitted for budget reasons. The [Pipelock example profile](../examples/pipelock/agent-review.toml) excludes generated protobuf, dependency, `testdata`, and selected lock-file paths; another repository must choose exclusions appropriate to its source and fixtures.

The shared [caller/profile validator](../scripts/agent_review_contract.py) requires the exact maintained caller template, named secret mappings, identity gate, event, permission ceiling, and trusted source SHA. Its executable revision and expected pin must be selected by trusted default-branch code, never by the proposed caller's contents. It also requires GitHub's caller `github.workflow_ref` to name that same `.github/workflows/agent-review.yaml`, so another workflow file can't call the shared engine behind a matching decoy caller. The local caller form is accepted only in `pipelab-org/agent-review`. Profiles and workflows are read through one bounded no-symlink reader.

## Credentials and spending

Callers map `ANTHROPIC_API_KEY`, `ANTHROPIC_API_KEY_2`, `OPENAI_API_KEY`, and optional `ORG_MEMBERS_TOKEN` from repository or organization secrets. The membership token needs only Members:read and is used only by the organization API. Each is individually optional; at least one configured provider is required for new inference. Don't use `secrets: inherit`, environment secrets, or a custom token for repository operations. The caller repository's `github.token` handles GitHub operations. Hosting the engine here doesn't supply this repository's secrets to any caller. See GitHub's [secret passing rules](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows#using-inputs-and-secrets-in-a-reusable-workflow).

The primary model remains `anthropic/claude-sonnet-5-5`, with `gpt-6-luna` as the configured OpenAI fallback. Only a reviewed central configuration change can select models. The second Anthropic key is used only after explicit billing rejection of the first. An absent first key skips both Anthropic slots, and an orphaned second key is ignored. Missing providers are skipped before inference.

Fallback requires a structured rejection with HTTP status 400, 402, or 429: Anthropic `error.type = "billing_error"`, Anthropic `error.type = "invalid_request_error"` with `credit balance is too low` in its message, or OpenAI `error.code = "insufficient_quota"`. Anthropic's [SDK billing schema](https://github.com/anthropics/anthropic-sdk-python/blob/v1.15.0/src/anthropic/types/shared/billing_error.py#L11) and [billing description](https://github.com/anthropics/anthropic-sdk-python/blob/v1.15.0/src/anthropic/types/beta/sessions/beta_managed_agents_billing_error.py#L23), plus [the pinned reviewer's legacy recognition](https://github.com/the-pr-agent/pr-agent/blob/8e5a9295973b24af4b70cafd0b660a230811ef9e/pr_agent/tools/pr_reviewer.py#L83), define those signals. Timeouts, dropped connections, ordinary rate limits, authentication errors, malformed output, and truncated completions fail without another paid attempt. Rejected slots remain retired for that run. Both completion-client and transport retries are disabled.

The operator budgets are three successful completion calls, a 90,000-token planning/context ceiling, 16,000 output tokens per call, a 300-second provider timeout, and a 25-minute review job. The finding limit uses the [pinned upstream default of three](https://github.com/The-PR-Agent/pr-agent/blob/8e5a9295973b24af4b70cafd0b660a230811ef9e/pr_agent/settings/configuration.toml#L180). This controls the requested key-issue output; it doesn't guarantee that additional defects appear in the summary. Security concerns remain a separate required field. These aren't claims about model capacity or monthly dollar limits. Oversized reviews list omitted files and fail as incomplete. Actual provider usage is reported when available, without prompts or credentials; provider account/project limits remain the spending backstop. Compare measured usage with current provider prices before changing a budget.

Inline key issues remain enabled because findings are published as resolvable threads; upstream defaults to summary-only output. The shared rubric follows the [pinned upstream prompt](https://github.com/The-PR-Agent/pr-agent/blob/8e5a9295973b24af4b70cafd0b660a230811ef9e/pr_agent/settings/pr_reviewer_prompts.toml#L10-L19): use the supplied hunks, avoid speculation about unseen code, and prefer no findings over unsupported ones. A deliberate behavior change alone isn't a defect.

Key issues use upstream's full-body marker identity to suppress exact repeats. Generic persistent inline comments remain disabled because their truncated-body identity can also match a changed finding. Persistent summary state remains disabled so earlier completion digests stay verifiable. Within one run, the adapter also suppresses an attempted repeat of a verified inline publication after re-reading its exact root, body, path, author, review, and commit. A changed finding still publishes. An ambiguous publication error aborts the run before upstream can retry it; incomplete publication never creates reusable success evidence. Inline reuse trusts only roots verified in the current run. A fresh run starts with no verified roots, so manually starting another review may duplicate comments if the first write partially persisted. Inspect the existing publication before retrying.

Authorized review jobs serialize by caller repository and PR, after admission, with `cancel-in-progress: false` and `queue: max`. This keeps a later command from silently replacing a pending one. Reuse avoids repeat inference for an already completed identical snapshot. GitHub concurrency remains repository-scoped, so a shared workflow doesn't create an organization-wide provider quota. See [concurrency behavior](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

## Failure visibility and permissions

Top-level permissions are empty. The caller job allows only `actions: read`, `contents: read`, `issues: write`, and `pull-requests: write`, which are the ceiling for its children. Source binding has no token permissions; admission has `pull-requests: read` and no provider secrets. The container keeps the existing checkout and publication permissions. Provider secrets appear only on the inference step. Called workflows can't elevate their [caller's permission ceiling](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations#access-and-permissions-for-nested-workflows).

The separate host-run notifier depends on source, admission, and review results. It uses only `pull-requests: write`, with no container, checkout, artifact downloads, provider secrets, or model. It uploads only its allowlisted notification outcome file. It repeats the original command/identity checks, validates the original repository and PR number, and re-reads same-repository/open-PR eligibility even when admission produced no outputs. It creates or updates a bot-owned status comment for that run using fixed text, captured commits when available, and an Actions link. Unauthorized commands, plain issues, closed PRs, and forks get no notification. Exception bodies, PR titles, branch names, model text, and logs aren't copied into comments. GitHub documents the [issue-comment endpoint's permission alternatives](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment).

This covers failures scheduled through the dependency graph: checkout, profile validation, missing credentials, provider/output/coverage errors, changed commits, container startup, review timeout, and cancellation when GitHub schedules the notifier. Whole-workflow cancellation, invalid YAML, an unavailable reusable workflow, and runner/GitHub outages can prevent the notifier from running. A failed notification keeps Actions red. See GitHub's [needs results](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#needs-context) and [status functions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions).

## GitHub request policy and failure diagnostics

GitHub's [best practices for the REST API](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) and [rate-limit rules](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) set the policy. The workflow token is limited to 1,000 requests per hour per repository, and a throttled response is a 403 or 429 (a primary limit shows `x-ratelimit-remaining: 0`). The pinned provider sends with no pacing and no retries by default. [The reliability module](../scripts/review_reliability.py) applies the policy to the adapter's existing GitHub calls: the provider's client, the follow-up reads, and the inline-reply client.

- **Serial, spaced writes.** Requests are issued one at a time. The common configuration sets `[github] seconds_between_writes = 1`, the documented minimum between mutative requests, and the adapter's client honors it.
- **Only reads are retried.** A throttled GET or HEAD is repeated after the server's own instruction: `Retry-After`, else the `x-ratelimit-reset` time when `x-ratelimit-remaining` is 0 (plus one second, as PyGithub does), else one minute, doubling per consecutive failure. A `Retry-After` or reset header that is present but unusable is never guessed at: the run stops. Server errors and network errors are not retried. A POST, PATCH, PUT or DELETE is never repeated, whatever the response, because the first attempt may have persisted; this keeps the ambiguous-publication abort intact. The provider's own `api_retries` stays off, since its stock retry class allows POST and every 5xx. The provider also re-runs a rate-limited diff read five times by default (`ratelimit_retries`, sleeping 2 to 16 seconds between tries) after the policy has already decided to stop; the common configuration sets one try.
- **Bounded.** Total waiting per run is one provider timeout (`ai_timeout`, 300 seconds). The review job allows 25 minutes and three completion calls of up to 300 seconds, so the worst case of every wait spent and every call timing out stays under the job limit; a test enforces it. This is an operator budget, not a GitHub number. An exhausted primary limit usually resets later than that, so the run fails at once with the reset time instead of sleeping until the job is killed. PyGithub's own ten-retry ceiling still applies per request.
- **Before any model spend.** A rate limit during provider setup, verified-record reads, scope comparison or the incremental delta ends the run before inference and before the running-status comment. The old fallbacks (treat unreadable proof as absent; fall back from incremental to full review) still apply to every other failure, but never to a throttle.

Every run records an allowlisted outcome. The adapter appends a fixed table to the Actions step summary and writes the same facts to `outcome.json`, uploaded as the `agent-review-outcome` artifact on success or failure. That name is separate from `agent-review-completion`, which stays exactly one `completion.json` from a successful run. Artifacts are immutable per workflow run and a re-run attempt shares its run's artifacts, so the diagnostic uploads set `overwrite: true` (a re-run replaces the earlier attempt's record instead of failing on the name) and `continue-on-error: true` (a failed diagnostic upload never turns a review red); the completion upload keeps neither. The record holds the phase (`configuration`, `provider_init`, `context`, `review`, `inference`, `publication`, `completion`), a category (`rate_limit_primary`, `rate_limit_secondary`, `rate_limit_unknown`, `authentication`, `forbidden`, `not_found`, `validation`, `client_error`, `server_error`, `network`, `review_abort`, `interrupted`, `unexpected`), the HTTP status, validated rate-limit headers (limit, remaining, used, reset, resource, seconds until reset, `Retry-After`, and the names of any malformed headers), the retry decision, a model provider's HTTP status kept apart from GitHub's, the count of throttle waits and seconds spent, and the first and last GitHub error responses with a label such as `GET repos/pulls/files` built from URL structure. It never holds a server or model message, response body, header other than those named, request URL, or credential. A rate limit that upstream code handled and hid still shows in the counts. Which of primary and secondary applies comes from the headers and, failing that, PyGithub's own message classification; with neither, the category is `rate_limit_unknown`.

The failure notifier keeps its fixed comment text. When its own GitHub call fails, for example because the same repository limit is exhausted, it records the same schema locally (`phase: notification` plus the failing operation) in its step summary and a runner-local file, then exits with its existing message so Actions stays red. The job uploads that file as `agent-review-notifier-outcome`, including when notification fails. Offline fixtures cover all of this, including the real PyGithub requester against a loopback server; they do not show how many requests a real review makes, and which endpoint exhausted the production runs is still unknown. The admission step's `gh api` call, the reply job's policy resolution, and its trusted-source lookup are unchanged and still fail without this record. Whether the artifact service accepts an upload from a rate-limited token needs live proof.

## Finding challenge before publication

Every nonempty review uses two discovery calls before publication. The first reads the diff and declares `source_requests`, an explicit list of repository-relative file paths (which may be empty). The adapter adds the key to the pinned review prompt's own `PRReview` definition and example, so the model sees one output contract. An omitted key and a key that is present but malformed both fail the run before anything is published, and only an explicit empty list means that no extra source is needed. If a future pinned prompt no longer has the expected definition, configuration is refused rather than guessed at. The second reads the same diff, full current candidate files, requested current files, PR description and prior threads. It can add candidates even when the first call found none. Candidates from both passes reach the existing challenge; omission from the second response never silently resolves an initial candidate.

Requested files come only from the admitted repository at the captured head through GitHub's [Contents API](https://docs.github.com/en/rest/repos/contents#get-repository-content). Paths cannot select another repository, revision, URL or command. Declared exclusions and supported-file policy apply to these reads too: an excluded or unsupported path is never read. Malformed request containers, read failures that don't determine the file's state at the admitted head, and oversized evidence prevent successful completion. A leading `./` is normalized; other invalid file paths are named unavailable without a read. A path that is determinately unavailable at that head (not found, deleted by this change, excluded, not a regular text file) doesn't fail the run: the model is told it could not be supplied, with the reason, and the completion record lists it. That is a named gap, never evidence that the file lacks a check. Source remains untrusted data, not executable instructions. This is one bounded source-read step, not autonomous tool use or repository-wide search.

For a changed file, the provider's copy is used when it loaded one. The pinned provider returns an empty string, without any flag, for files it did not load (for example past its full-content file limit or after a failed read), so an empty copy of a non-deleted file is read from the Contents API at the admitted head instead of being presented as an empty file. A request for more files than PR-Agent's own per-review full-content limit (`MAX_FILES_ALLOWED_FULL`, 50 in the pinned release) fails the run before any read, so untrusted PR text cannot spend an unbounded number of workflow-token API reads. The completion record's quality section names the requested and supplied paths and a SHA-256 of the exact discovery request, so the evidence behind the second pass is bound to the snapshot like the challenge's.

The final call challenges any candidates against the supplied source and discussion. The existing three-successful-call ceiling, token planning limits, output limits and billing-only fallback remain. A clean two-pass result uses two calls; a result with candidates uses three. This costs an additional discovery call compared with the previous empty-result path. Only one initial diff call now fits the allocation: a diff requiring more calls reports incomplete coverage rather than omitting files. No-candidate results still do not establish recall.

The challenge receives complete current candidate files and requested context, every reviewable patch, the reviewable file inventory, the full PR description and prior inline threads. It retains the discovery pass's diff and supplied source because supporting or refuting code can lie in another changed file. A large pull request can exceed the existing token budget, which ends the run unsuccessfully after the second call rather than truncating evidence. Excluded or unavailable code cannot establish that a check is absent. A rebuttal or declared hold cannot excuse a newly demonstrated defect.

Every candidate needs a structured disposition. A published finding names a triggering state, consequence, repair and exact current source lines. For a located candidate, the prompt requires the evidence range and its exact complete-line quote to cover the entire candidate range; a shorter quote is refused even when its text matches. Its title names the failure. Duplicate scenarios and acknowledged decisions remain unresolved findings in the summary and structured completion, with their evidence, without another inline thread. Unsupported claims are recorded in the challenge audit. Malformed or partial output, unreadable history, mismatched source evidence and oversized context prevent successful completion. A second model response isn't independent review, execution evidence or a measured precision guarantee.

The challenge response accepts strict JSON, optionally wrapped in one complete lowercase `json` code fence with three backticks and no surrounding prose. This is a narrow envelope from [CommonMark fenced code blocks](https://spec.commonmark.org/0.31.2/#fenced-code-blocks). Removing that envelope uses no additional model call. Duplicate JSON fields, extra documents, incomplete fences and invalid decisions still fail validation. Completion records and other trusted JSON don't accept this envelope.

## Completion data for review checks

A successful completion keeps the existing `agent-review-status:v1` line. Its `digest` is the SHA-256 of the whole summary comment after `<!-- agent-review-result:v1 BASE64 -->` is appended. The status comment repeats that same result comment. The payload is UTF-8 JSON encoded with standard Base64. It names `repository`, a positive integer PR `number`, full `base` and `head` SHAs, `depth` (`default` or `deep`), completion `key`, a positive integer summary comment `summary`, and a `findings` array. JSON `true`, `false`, a float, a string, zero, or a negative number is not an integer identifier, so that record is malformed and is not reused. The digest stays on the status line because it covers the summary that contains the JSON. Each finding carries `path`, `line`, `end_line`, `title`, and `body`. Lines are positive integers; a security concern without a changed location uses `path: "unknown"` and null lines. The pinned PR-Agent review schema specifies the exact literal `No` for absent security concerns. Any other nonempty value remains a finding. Path, title, body, and that security text have surrounding whitespace removed first. The prompt's literal block scalars keep a trailing newline, and the published review strips those fields before it anchors a comment.

Consumers must verify the bot account, repository and PR, current head, requested depth, status key, and summary identity. They must hash the summary body and compare it with the status digest, then read the findings from that summary. A missing, malformed, or different copy is incomplete and is not reused. The structured findings let checks read the summary without inferring results from rendered HTML. Inline review threads still need their own resolution checks. This record reports a completed static review; it does not authorize a merge.

## Trusted model policy by depth

The central `[review_depth.default]` policy selects `anthropic/claude-sonnet-5-5`, `medium`, and the existing `gpt-6-luna` fallback. `[review_depth.deep]` selects `anthropic/claude-opus-5-5`, `high`, and the same OpenAI fallback. These Claude IDs come from the [publisher's model overview](https://platform.claude.com/docs/en/models/overview). The normal policy handles inline questions, including questions on a deep-review finding. Profiles still permit only instructions and exclusions. Model choice is operator policy; it doesn't establish quality or recall.

## Automatic inline replies

Only a newly created `pull_request_review_comment` reply qualifies. The running caller must be the exact maintained file at GitHub's PR merge ref. Remote callers keep their immutable shared-source pin. For this repository's local caller, a workflow-only step resolves an immutable default-branch source commit before checking out or executing repository code; the PR merge commit cannot supply Python. The loaded caller is validated as data, and caller policy comes from an immutable default-branch commit. See GitHub's [review-comment event contract](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_review_comment). Repository writers who can modify workflows remain within GitHub's normal same-repository workflow trust boundary. No PR code is checked out or executed by the shared engine.

Admission re-fetches the triggering comment and compares its identity, body, creation time, thread root, review, path, PR URL, and commit fields with the event. GitHub can store `updated_at` one second after `created_at` on a reply that wasn't edited, so that clock step isn't treated as an edit. The PR must remain open, within the same repository, at the captured commits. Josh's login and numeric ID are fixed. Other human authors require an active membership returned by GitHub's [organization-membership API](https://docs.github.com/en/rest/orgs/members#get-organization-membership-for-a-user), rather than `author_association`. Private membership may require an optional Members:read `ORG_MEMBERS_TOKEN`; missing visibility, pending membership, or API failure refuses the reply. Bots, edited events, reruns, mismatched actors, stale roots, and unrelated bot threads don't qualify.

The root's comment ID, review ID, path, commit, and body hash must appear in this workflow's verified completion artifact. The referenced review and root must still belong to the exact GitHub Actions bot account and the current head. A bot username or copied marker alone never grants ownership. Old or edited roots require a fresh review rather than an answer that assumes current code. Source/profile/config changes also invalidate the old context.

The model receives only the static root finding, its diff hunk, thread history, and question as untrusted data. It can't fetch URLs, invoke tools, select credentials, change settings, or select the publishing target. Existing token and provider-call budgets apply, with the same billing-only fallback. Admission is checked again after inference. A pending same-thread comment appears before inference and becomes either the answer or a fixed incomplete message. Publication is re-read through the [review-comment API](https://docs.github.com/en/rest/pulls/comments); upstream's error-swallowing reply helper isn't used. The triggering comment ID deduplicates publication, including concurrent duplicates. Rejected requests and failures before pending publication remain visible in Actions; runner/container failure can prevent a thread notification. A failed or pending response isn't retried for the same triggering comment; post a new reply to try again.

## Immutable completion and incremental coverage

New completions retain the v1 status/result envelope and add a `version: 2` payload. That JSON plus the separately computed summary `digest` is uploaded once as `completion.json` in an `agent-review-completion` artifact. The artifact and its archive digest must match the structured comment. The originating run must have completed successfully on its first attempt, for the designated maintainer's issue-comment event, in the exact caller workflow, with the expected caller revision and referenced shared-source SHA. GitHub's [run API](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run), [artifact API](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact), and [immutable v4 artifacts](https://github.com/actions/upload-artifact#v4---whats-new) supply provenance that a shared bot identity alone can't provide. Expired, missing, modified, or unavailable evidence never suppresses a fresh review. Archive redirects never receive the GitHub authorization token.

The `context` object binds repository, integer PR number, full base/head/reviewer/profile SHAs, profile and central-config hashes, configured models, and depth. Its canonical sorted JSON determines the completion key. `run_id` identifies the proof run. `roots` binds published inline root IDs, review IDs, paths, commits, and body hashes. Existing finding fields remain available for sweep consumers. Each summary is published separately and preserved so its digest and earlier findings remain verifiable.

Every `scope` names `kind`, `from`, `to`, `parent`, and `full_head`. A `full` scope starts at the captured PR base, has no parent, and sets `full_head: true`. An `incremental` scope starts at a verified parent's full head SHA, names that parent's run ID, and sets `full_head: false`. An identical-content delta extends the same chain without inference. A command on an already verified identical head creates only a reuse notice. No timestamp selects an anchor.

Consumers must validate every parent back to a completed full review under the same policy and base relationship, then prove commit ancestry to the current head. Compare APIs use immutable full SHAs. The prior and current merge-base relationship must match. Missing or cyclic parents, force-push divergence, policy changes, or changed merge-base context trigger full review. Unsupported delta content also falls back to the existing full-review path. GitHub's [compare contract](https://docs.github.com/en/rest/commits/commits#compare-two-commits) supplies at most 300 changed files; reaching that boundary triggers full review rather than trusting a potentially truncated list. UTF-8 file contents are fetched at the exact prior/current SHAs and converted to the existing `FilePatchInfo` objects. Declared exclusions and the existing supported-file policy still apply.

An incremental run's findings describe only its delta. It doesn't independently certify a full-head review, close earlier findings, or resolve old threads. Sweep consumers must retain earlier findings across the verified chain and inspect thread resolution separately. Consumers that understand only v1 full-review records must reject incremental v2 records until they implement chain validation.

Before adoption, live proof still needs real provider acceptance, Actions artifact visibility and run metadata, membership permissions, default-branch and merge-ref caller composition, current-head inline publication, and cross-repository operation. Offline fixtures don't establish any of those account-level conditions.

### Related-source findings and repeated candidates

A verified defect caused by the diff can be located in an unchanged requested consumer. Findings outside the new-side ranges of a diff hunk also use this route. Such findings stay in the summary and structured completion with their real source locations; they do not create an inline thread on a fabricated changed line. The same source-quote and failure-scenario checks apply. Unrequested or unavailable source is named in the challenge and cannot support a published finding; an unsupported disposition allows the remaining candidates to proceed.

The challenge can mark a candidate as `duplicate-candidate` only by naming an earlier candidate that it also publishes. The disposition records the shared failure scenario. Self-references, forward references and references to discarded candidates fail validation. A duplicate security concern remains visible as a security concern. This avoids relying only on exact wording to identify repeats between the two discovery passes.

Completion evidence and the bound summary must fit the existing data budget before the status can become successful. Summary-only and retained findings replace the renderer's issue all-clear label with a reference to the remaining findings. Unavailable source is disclosed in the summary and qualifies the assessment; a correctness finding alone does not imply a security concern.

## Historical replay

An operator can measure a reviewer revision against saved pull request snapshots without publishing anything. See [Historical review replay](review-replay.md).

### Large-context replay diagnostic

The replay CLI accepts an explicit `--large-context-diagnostic` with `--depth deep`. This uses a 1,000,000-token context cap for the documented Opus 5.5 and GPT-6 Luna routes. Their published capacities are [1M tokens](https://platform.claude.com/docs/en/about-claude/models/overview) and [1,050,000 tokens](https://developers.openai.com/api/docs/models/gpt-6-luna). The preset refuses other configured routes. It changes both the operator context cap and PR-Agent's custom-model context fallback; the existing output reserve, timeouts, three-call ceiling, retries, source handling and publication validators stay in force. Complete requests must still fit on every remaining billing-fallback route.

This option exists only in the nonpublishing replay CLI. Normal reviews and replays without the flag retain the configured 90,000-token cap. A repository profile, snapshot or pull request cannot enable it. Results label `reviewer.context_policy` as `large-context-diagnostic` or `configured` and record both effective context settings. Diagnostic results test a different budget policy; compare only runs declaring the same policy, engine, profile and inputs. More context capacity permits more input spending and does not establish detection quality. Fixture responses remain mechanic evidence.
